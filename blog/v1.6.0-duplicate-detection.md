# v1.6.0: Duplicate Detection + 2-5x Faster — Knowledge Keeper MCP Grows Up

We just shipped [Knowledge Keeper MCP v1.6.0](https://github.com/zsc-glitch/knowledge-keeper-mcp) with two major improvements: a new duplicate detection tool and significant performance optimizations from v1.5.0.

## New: `knowledge_duplicates`

Ever saved the same thing twice? Or had two notes that say basically the same thing in different words? The new `knowledge_duplicates` tool finds them.

```json
{
  "tool": "knowledge_duplicates",
  "input": {
    "threshold": 0.7,
    "scope": "both",
    "limit": 10
  }
}
```

**How it works:**
1. Loads all knowledge points from the index
2. Computes [Jaccard similarity](https://en.wikipedia.org/wiki/Jaccard_index) between every pair
3. For `scope: "both"`, it weights title similarity at 60% and content at 40%
4. Returns groups of similar items with merge suggestions

**Example output:**
```
🔍 Duplicate Detection (threshold: 0.7, scope: both)

Found 2 groups of similar knowledge points (out of 47)

1. 🔗 Similarity 0.85 (2 items)
    - [note] Docker Multi-Stage Builds (2026-04-15)
    - [note] Docker Multi-Stage Build Guide (2026-04-18)
    💡 Suggest keeping "Docker Multi-Stage Build Guide" (kp-nt-...), merge the other

2. 🔗 Similarity 0.72 (2 items)
    - [decision] Choose Redis over Memcached (2026-03-20)
    - [decision] Caching: Redis vs Memcached Decision (2026-03-25)
    💡 Suggest keeping "Caching: Redis vs Memcached Decision" (kp-dc-...), merge the other

💡 Use knowledge_merge tool to merge duplicates
```

**Design decisions:**
- **Jaccard over embedding similarity**: Zero API keys means no embeddings. Jaccard on word sets is fast, deterministic, and requires zero dependencies.
- **Title weight > content weight**: Titles are usually the strongest signal for duplication. Two notes titled "Docker Builds" with different content are more likely duplicates than two differently-titled notes that happen to mention Docker.
- **Merge suggestions**: The tool doesn't just find duplicates — it suggests which one to keep (newest, or the one with the most tags), and links directly to `knowledge_merge`.

## From v1.5.0: 2-5x Faster Analytics/Export/Sync

v1.5.0 eliminated a subtle anti-pattern: 14 places were calling `searchKnowledge({ query: "" })` — running through the full search pipeline (load → filter → sort) just to get "all entries."

The fix: a public `loadAllEntries()` function in `core.ts` that reads `index.json` directly. No filtering, no sorting, no search overhead.

The worst case was in cloud sync: `searchKnowledge` was called **inside a loop** — once per remote item. 50 items = 50 full index loads. Now it reads once before the loop.
